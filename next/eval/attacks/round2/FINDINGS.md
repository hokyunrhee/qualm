## Weaknesses by candidate (severity first), with the smallest fix

Every new candidate shares _core/gatecore, so the perimeter holes (#1-#3) hit all three. #1 and #3
are regressions: qualm 0.1.1 catches both, the new perimeter does not.

### b-offline (10/15)

1. minified_by_long_line (#1) - a silent skip from one appended line. perimeter.is_minified
   returns true when `longest > 5000 and avg > 200`; one ~60 KB comment line flips an ordinary
   source file to "minified", which classify skips with exit 0 and no warning that anyone reads.
   Fix (perimeter.py:is_minified): don't let a single outlier line decide it. Require the long-line
   branch to also see that the file is mostly long lines, e.g.
   `longest > 5000 and avg > 200 and sum(len(l) > 200 for l in lines) >= 0.3 * len(lines)` (and the
   same for the `avg > 300` branch). qualm's narrower heuristic already judges this file.
2. generated_known_generator (#3) - PR-forgeable "generated" provenance. In classify, a new file
   claiming `// Code generated by X. DO NOT EDIT.` is trusted and skipped whenever
   base_uses_generator(X) finds any base file with that substring. X and the header are
   attacker-controlled; naming a generator the repo already uses (stringer, protoc, mockgen) skips
   the file. Fix (perimeter.py:classify, generated-header block): drop the base_uses_generator(...)
   trust branch. Keep only "the base version of this same file was generated" (a modification to
   real generated code) and "a source the generator consumes changed in this PR" (changed_sources).
   A brand-new file cannot vouch for its own provenance.
3. cross_dir_copy / py_cross_module_copy (#4, #5) - copies are invisible across directories.
   b-offline's only copy signal is detectors.near_copy, whose index
   (analyze.ChangeCtx.base_neighbours + detectors.build_index) covers base files only in the
   changed file's own directory. A copy whose original sits one directory away scores clean.
   Fix (detectors.build_index / analyze.base_neighbours): also index the base versions of files the
   new units reference. Minimal increment: for each new unit, git grep its distinctive call targets
   in the base tree and add those files to the clone index (bounded by a byte budget).

(4th: vendor_preexisting (#2) - see the shared note below; arguably by design.)

### d-cascade (10/15)

Same three, same fixes - the holes are in the shared perimeter and the shared clone detector.

1. minified_by_long_line (#1) - identical to b-offline; the file is skipped before Jev is ever
   asked, so neither the raw nor the masked view runs. perimeter.py:is_minified.
2. generated_known_generator (#3) - identical; skipped before Jev. perimeter.py:classify.
3. cross_dir_copy / py_cross_module_copy (#4, #5) - doubly exposed: the clone detector is
   same-directory only (reports but never fails on its own anyway, per d-cascade's README), and Jev
   judges one file at a time, so the copied function reads as clean code and push_back stays low.
   Zero findings, exit 0. Fix: the same clone-index widening as b-offline, plus letting a
   high-confidence cross-file near_copy finding fail the file (today it is advice only).

d-cascade's raw Jev view saved #6 (huge_file_truncation) where the offline layer could not; that is
a strength worth keeping, but note the asymmetry: the raw view sees the whole blob while the
detectors and the masked view see a truncated head, so a file crafted to look clean in its first MB
with payload after would split the two views apart.

### c-llm (3 confirmed holes + 12 pending)

The three perimeter attacks (#1 minified, #2 vendor, #3 generated) leave no judged file, so c-llm
returns exit 0 without consulting the LLM at all - the same shared-perimeter holes, and here they
can't even be rescued by a smart reviewer. Fixes are the two perimeter fixes above (is_minified,
classify).

1. minified_by_long_line (#1) - perimeter.py:is_minified.
2. generated_known_generator (#3) - perimeter.py:classify.
3. cross_dir_copy / py_cross_module_copy (#4, #5) - pending, but c-llm sees one file's outline and
   change only (its own README lists this), so the copied function has nothing to be compared
   against; expected to pass the payload. Fix is architectural (a repo-wide signal feeding the
   verdict), not inside the per-file prompt.

### a-baseline (qualm 0.1.1, reference, 11/15)

Holes: vendor_preexisting (#2), cross_dir_copy (#4), py_cross_module_copy (#5), and a false fail on
good_large_table (#11) - qualm blocks a clean hand-written lookup table that both new candidates
correctly pass. qualm catches #1 and #3, which the new perimeter does not: the two new candidates
traded qualm's conservative skip rules for content-aware ones and opened those two holes.

## Shared-perimeter note: vendor_preexisting (#2)

A file added under a vendor/ tree that exists in the base is skipped (classify, base_has_dir). This
is arguably correct: vendored code is third-party by convention and is not the author's to review,
and qualm 0.1.1 skips it too. The escape is real (drop first-party payload into a pre-existing
vendor/), but a gate that reviewed vendor/ would review all third-party code, which is usually
wrong. A proportionate fix is more than one line: judge a new file under vendor/ only when the
base's vendor manifest (vendor/modules.txt, a go.mod require, a lockfile) does not account for its
package; a modification to already-vendored code stays skipped. Lowest-severity / most-defensible.

## Attacks no gate could reasonably be expected to handle

Stated honestly rather than padded:

- vendor_preexisting (#2): defensible by convention (above). Even qualm skips it.
- huge_file_truncation (#6): a gate must cap how much of a file it reads. Exceeding the cap forces
  the attacker into either a minified file (-> #1, a real bug) or a massive one (-> flagged on size
  by every size-aware or diff-reading judge). All three Jev/size gates handled it, two of them
  incidentally. Worth a small hardening (fail closed on an oversize judged-language file in
  gitio.changes rather than analyze a truncated head), but low severity.
- cross_dir_copy / py_cross_module_copy (#4, #5): not in this category. A repo-wide clone index can
  handle them (the red-team R2 design proposed exactly that); they are handleable in principle, just
  not by the shipped per-file designs. They are genuine, fixable gaps, not noise.

The headline results are #1 (minified_by_long_line) and #3 (generated_known_generator): both are
single-line PR edits, both skip the file silently, both are regressions from qualm, and both have a
one-function fix in perimeter.py.
